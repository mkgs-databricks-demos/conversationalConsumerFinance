Constitution

Design principles.

These principles are the constitution of this system. Every component, every query, and every deployment decision is evaluated against them.

Security is enforced, not impliedEvery metric view requires a consumer_guid parameter with no default. A query without it fails — it does not return empty and does not fall back. Consumer isolation is enforced at the SQL layer, below the agent and the application.
Determinism over probabilityEvery metric has an exact SQL definition generated and tested from FIBO-informed semantics. There is no probabilistic graph traversal between a customer's question and their number.
One agent, not a swarmA single Genie agent per locale serves every question from three metric views plus a Knowledge Assistant. No routing layer, no agent-to-agent handoffs, no cross-agent governance gaps.
One codebase, any marketLocales are YAML configurations, not forks. The same 17 components deploy as an American, British, or Dutch bank with a single variable.
The ontology is inputFIBO definitions feed Genie Code, which generates deterministic, tested UC Semantics. The ontology's value is captured; its complexity is not inherited.
Every answer is auditableEach question produces an immutable MLflow 3 trace with 8 spans, streamed OTel metrics, and 7 automated alert rules (P0–P3). Any answer can be replayed for a regulator.
Fast at conversation speedEnzyme-optimized materialized views with liquid clustering keep query latency under 200ms and end-to-end response under 3s p99.
Architecture

Six layers. One platform.

Each layer has a single responsibility and a single consumer above it. Governance happens once, at the platform, and every layer inherits it.

Deployment

Three bundles, cleanly separated.

Bundle 1 is the infrastructure (UC catalogs, Lakebase, the Lakeflow SDP pipeline, jobs, and volumes) and ships to every environment. Bundle 2 is the full-spectrum data generator — dev and demo only, optional in production, where real source systems feed the same Bronze layer through the Genie Code mapping workflow. Bundle 3 is the application: the Databricks App, one Genie agent per locale, three parameterized metric views, and the UC Pages and Domain that give the agent its certified vocabulary.

Runtime

One question, end to end.

A consumer question enters through the API Gateway (JWT validated in ~5ms), passes session and consent checks in Lakebase (~2ms), rate limiting, and input sanitization, then reaches a single agent — no routing tier. The agent queries a parameterized metric view with the required consumer_guid; a post-query SQL predicate validator confirms the consumer filter, while ai_decide checks topic, PII, appropriateness, and language in parallel. The full trace lands in MLflow 3.

Semantic Layer

Two-layer metric views.

The semantic layer is a two-layer pattern. Layer 1 is a set of Enzyme-optimized materialized views (no row-level security, no parameters) rebuilt incrementally from the 14 FIBO-aligned Silver tables — they exist purely for speed. Layer 2 is the consumer-facing surface: three parameterized metric views that require consumer_guid, expose 12 measures and 14 dimensions, and carry locale synonyms. The single Genie agent uses 4 of its 50 allowed sources: the three metric views plus the Knowledge Assistant volume.

Security

Sixteen controls, three rings.

Hard enforcement (~8ms, in the request path): JWT validation, session and consent checks in Lakebase, rate limiting, input sanitization, the required-parameter rule, the consumer filter, and the SQL predicate validator. Soft validation (~200ms, parallel): ai_decide topic, cross-consumer PII, appropriateness, and language checks. Audit (async, 0ms): MLflow 3 traces, nightly anomaly detection, cross-consumer correlation, and SQL pattern analysis by Genie Code.

The parameterized metric view is the keystone: consumer_guid is a required parameter with no default. A query without it fails — the agent cannot construct a query that reads another customer's data. No other consumer AI architecture in the market provides this level of data isolation at the SQL layer.

Data Platform

Medallion with FIBO-aligned Silver.

Bronze holds raw streaming events. Silver applies the FIBO-aligned model: 14 Phase 1 tables with SCD2, CDF, and DECIMAL(20,4) money types — with party_relationship as the join path from party to account. Gold is the two-layer pattern described above, feeding one Genie agent per locale. In production the simulator is replaced by core banking, card processing, and payments systems mapped through the same event contracts.

Sessions & Memory

Lakebase session lifecycle.

Lakebase (via PgBouncer) owns session state: first request creates a session bound to the consumer GUID with language and consent state; subsequent requests validate the session token in ~2ms without revalidating the JWT; expired sessions get a 401 and reauth. Vector Search provides long-term memory — past conversations retrieved semantically so the agent remembers context across sessions.

Multi-Locale

One codebase. Deploy as any bank.

All 17 components — simulator, SDP pipeline, metric view templates, 60 UC Page templates, agent template, app, validator — are locale-neutral. Locale YAML files carry currency, payment rails, account naming, holidays, merchant mixes, and language. Deploying a new market is a config file and a bundle variable.

Orchestration

Single agent. Three metric views.

The app layer injects consumer_guid into every agent call. The Consumer Banking Agent answers from the three metric views and the Knowledge Assistant volume, then every generated SQL statement passes the predicate validator with ai_decide running in parallel. There is deliberately no router, no multi-agent graph, and no fallback path that bypasses the semantic layer.

Delivery

12 weeks to production.

Phase 1 (weeks 1–2, Foundation): synthetic data generation, FIBO mapping, Silver tables, first metric views. Phase 2 (weeks 3–5, App Spike): consumer app, security pipeline, first working demo. Phase 3 (weeks 6–9, Expansion): full metric coverage, multi-locale, observability, benchmarks. Phase 4 (weeks 10–12, Production): load testing, runbooks, alerting, go-live.
